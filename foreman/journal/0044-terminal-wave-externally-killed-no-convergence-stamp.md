Every RESUME after that re-ran wave-11 execute (a long claude -p call) and the process was stopped from outside mid-execute — cleanly, no error/OOM/stderr, just SIGTERM/SIGKILL. - **observation**: (1) A killed run leaves the checkpoint at `status:running` (stale), which a plain `--resume` re-enters fine (no lock corruption) — good. (2) But Foreman has NO "deliverable already proven, just missing the convergence stamp" recovery: each resume re-runs the long execute (redundant, since gate was already green), re-exposing it to whatever is killing it — a livelock against an external reaper. (3) The driving session VERIFIED completion out-of-band (`node --test` = 778 pass / 0 fail / 0 skip incl the pinned subsystem + 6-stage pipeline) and treated the feature as done, which is the only way it finished. Likely killer: a reaper (zombie-hunter / anchor) mis-flagging the build's `claude -p` workers as orphaned, OR a host resource/timeout limit — UNCONFIRMED, worth John running down so it doesn't bite other long terminal-wave runs.
- **outcome**: friction — a complete, green build could not self-finish; needed manual out-of-band verification to call it done. Suggested: (a) a `--attest-wave-green` fast path that, when the gate is already GREEN on resume, skips re-execute and goes straight to review/convergence (don't re-pay the long execute); (b) surface a distinct "COMPLETE-BUT-UNSTAMPED (gate green, convergence not recorded)" terminal state instead of leaving a stale `running`; (c) protect the build's child PIDs from the reaper (ownership tag).
